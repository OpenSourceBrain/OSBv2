# Data and storage model

What the OSBv2 platform persists, where, and for how long. Every statement is tied to a
file and symbol; the last section lists what the code consulted here does **not** settle.

## Two stores, one rule

The platform keeps **metadata** in the workspaces Postgres database and **content** on a
per-workspace Kubernetes volume. Nothing in the database holds file bytes, and nothing on
the volume holds ownership or names.

- Metadata store: Flask-SQLAlchemy, `applications/workspaces/server/workspaces/database.py`
  (`db`), used with `db.session.no_autoflush` in
  `applications/workspaces/server/workspaces/service/crud_service.py` (`:310`, `:364`)
  and repositories in `applications/workspaces/server/workspaces/persistence/`
  (`WorkspaceRepository`, `WorkspaceResourceRepository`, `OSBRepositoryRepository`,
  `VolumeStorageRepository`, `TagRepository`, imported at `crud_service.py:22-28`).
- Content store: a PVC per workspace, described under "Volume model" below.

## Schema: workspaces database

`applications/workspaces/server/workspaces/persistence/models.py` is the only schema
description in this repository. It is **autogenerated**: its header says "Autogenerated
SQLAlchemy models based on OpenAlchemy models", and each entity is a `typing.Protocol` /
`TypedDict` façade assigned from `open_alchemy.models` (`WorkspaceEntity: TWorkspaceEntity =
models.WorkspaceEntity`, `:222`; likewise `:318`, `:414`, `:508`, `:693`, `:786`, `:956`).
So this file gives the **table and attribute names, required-ness and defaults**, not the
column types, indexes or foreign-key constraints — those are emitted by OpenAlchemy from
the OpenAPI schema (see `devdocs/api-contracts.md`).

### `WorkspaceEntity` (`models.py:13-222`)

Required: `name`, `description`.
Optional: `id` (int), `timestamp_created`, `timestamp_updated`,
`last_opened_resource_id` (int), `thumbnail` (str), `gallery` (sequence of
`WorkspaceImage`), `user_id` (str — "Workspace keycloak user id, will be automatically be
set to the logged in user"), `publicable` (bool, default `False`), `featured` (bool, default
`False`), `license` (str), `collaborators` (sequence of `WorkspaceCollaborator`),
`storage` (single optional `VolumeStorage`), `tags` (sequence of `Tag`), `resources`
(sequence of `WorkspaceResourceEntity`).

Ownership is the `user_id` column, a Keycloak subject — the same value the API reads back
as `keycloak_user_id()` and compares in `WorkspaceService.is_authorized`
(`crud_service.py:329-333`). It is stamped on create when the caller omits it:
`crud_service.py:211-215`.

### `WorkspaceCollaborator` (`models.py:225-318`)

Required: `user_id` (str — "Workspace Collaborator keycloak user id"). Optional: `id`.
Reached only through `WorkspaceEntity.collaborators`.

### `WorkspaceImage` (`models.py:321-414`)

Required: `image` (str). Optional: `id`. The gallery of a workspace, reached through
`WorkspaceEntity.gallery`.

### `VolumeStorage` (`models.py:417-508`)

Required: `name` (str — "StorageVolume name"). Optional: `id`. Referenced optionally from
`WorkspaceEntity.storage`, and served by an administrator-only service
(`VolumestorageService.is_authorized`, `crud_service.py:516-518`).

### `OSBRepositoryEntity` (`models.py:511-693`)

Required: `name`, `repository_type`, `content_types`, `uri`.
Optional: `id`, `summary`, `auto_sync` (bool, default `True`), `default_context`,
`thumbnail`, `user_id` (str — "OSBRepository keycloak user id"),
`timestamp_created`, `timestamp_updated`, `tags`.

`repository_type` is one of `dandi`, `figshare`, `github` (docstring at `models.py:544-545`).
`content_types` is stored as one **comma-separated string**, not a list: the service builds
it by concatenation in `OsbrepositoryService.to_dao` (`crud_service.py:486-498`) and splits
it back in `content_types_list` (`:504-506`).

### `Tag` (`models.py:696-786`)

Optional: `id`, `tag` (str) — the only entity with no required column. Shared by
workspaces (`WorkspaceEntity.tags`) and repositories (`OSBRepositoryEntity.tags`);
public for read (`TagService.is_authorized`, `crud_service.py:612-614`).

### `WorkspaceResourceEntity` (`models.py:789-956`)

Required: `name`, `resource_type`.
Optional: `id`, `status` (str, **default `"p"`**), `timestamp_created`,
`timestamp_updated`, `timestamp_last_opened`, `origin` (str), `workspace_id` (int),
`folder` (str).

Two columns carry encoded structure:

- `origin` is a **JSON string** in the database. `WorkspaceresourceService.to_dao`
  `json.dumps` it on the way in (`crud_service.py:529-531`) and `to_dto` `json.loads` it
  on the way out (`:545-548`).
- `folder` is the resource's path on the volume; the API field is called `path`. The
  mapping is explicit: `ws_dict['folder'] = ws_dict['path']` (`:532-534`), `dto.path =
  resource.folder` (`:556-557`), and an empty/missing `folder` defaults to the resource
  `name` (`:540-541`).
- `status` default `"p"` (pending) is what the import pipeline keys off: a pending
  resource with an `origin` triggers a copy (`crud_service.py:584-588`, `:48-53` of
  `helpers/etl_helpers.py`).

### Relationships, as far as the code shows

`Workspace` 1-n `WorkspaceResourceEntity` (via `resources`, and `workspace_id` on the
resource); `Workspace` 1-n `WorkspaceCollaborator`, 1-n `WorkspaceImage` (gallery),
0-1 `VolumeStorage`, n-n `Tag`; `OSBRepositoryEntity` n-n `Tag`. The service layer assumes
an ORM cascade of resources on workspace write: `WorkspaceService.to_dao` detaches
`resources` before constructing the entity and rebuilds them (`crud_service.py:378-387`),
and `clone` sets `workspace.resources = []` on the copy (`:321`).

There is **no entity for a notebook run, a workflow, a job or an event**. See "Platform
state versus Argo state" below.

## Volume model

### One PVC per workspace

The name is derived, never stored: `WorkspaceService.get_pvc_name(workspace_id)` returns
`f"workspace-{workspace_id}"` (`applications/workspaces/server/workspaces/service/crud_service.py:182-184`).
A workspace's content is therefore identified by its row id; losing the row loses the
handle on the volume.

### Creation and sizing

- Created on workspace create (`WorkspaceService.post` → `ensure_volume`,
  `crud_service.py:211-224`, `:235-244`) and on clone (`:325`).
- `create_volume` is idempotent ("``create_volume`` is idempotent: it is a no-op when the
  PVC already exists", `:240-241`), so a workspace whose volume vanished is repaired on
  the next create/clone rather than failing to mount.
- Size comes from the **owner's quota**, read per request:
  `get_workspace_volume_size` → `get_pvc_size(user_id)` (`crud_service.py:230-233`). The
  sizing rules themselves are documented in `devdocs/user-quotas.md`; this document does
  not restate the numbers.
- Viewing a workspace schedules a **background** create so a plain read never blocks on
  Kubernetes/NFS (`ensure_volume_background`, `:246-280`). It is skipped when the caller is
  not the owner (`:257-258`) so a visitor cannot create a PVC sized by their own quota, and
  a per-process `set` + lock (`:179-180`) stops the portal's polling loop from spawning one
  thread per poll.
- Opening a workspace **blocks** instead: `ensure_volume_ready` returns immediately if
  `volume_is_ready`, else creates and waits up to 5 s (`:282-303`). When it is still not
  ready the controller answers 503 with `{"error": "volume_not_ready", ...}`
  (`workspaces/controllers/workspace_controller.py:118-139`), deliberately, instead of
  spawning a pod whose volume would fail to mount.

### Mount point and lifecycle

- Inside Argo pods the PVC is mounted at **`/project_download`**, writable:
  `shared_directory = f"{pvc_name}:/project_download:rwx"`
  (`workspaces/service/workflow.py:50`, `:65`, `:231`). The clone job mounts the source at
  `/source` and the destination at `/project_download:rwx` (`:96-97`).
- Resource paths are relative to that mount: the scan result strips
  `/project_download/` from reported paths (`workspaces/controllers/events.py:16-17`), and
  resource deletion runs `rm -Rf project_download/<resource_path>` in a pod
  (`workflow.py:24-31`). Paths are validated to stay inside the volume
  (`resource_folder`, `helpers/etl_helpers.py:56-61`: returns `""` for absolute paths or any
  `..` component).
- Clone copies content, not metadata: `cp -R /source/* /project_download && chown -R
  1000:1000 /project_download` (`workflow.py:99-102`).
- **Retention equals the workspace's lifetime, and both directions are explicit:**
  creation creates the PVC, and `WorkspaceService.delete` calls
  `delete_persistent_volume_claim(f"workspace-{id}")` after deleting the row and its
  resources (`crud_service.py:445-458`), then removes the workspace's directory under
  `Config.STATIC_DIR` if present (`:460-464`).
- Nothing in the code consulted here **reconciles** PVCs against database rows: no listing
  of volumes to find orphans, and no reaper. A PVC whose row was dropped by other means is
  not cleaned up by anything this document found.

### The NFS export

The volumes are backed by the platform's NFS server (`nfsserver` is a declared dependency of
`workspaces` — `applications/workspaces/deploy/values.yaml`, and the `CH_NFSSERVER_*`
variables in `applications/workspaces/server/test/values.yaml:1097-1098`). The **export
size (the 240Gi figure) is not asserted here**: none of the files read for this document
(`persistence/models.py`, `service/crud_service.py`, `service/workflow.py`,
`helpers/etl_helpers.py`, `controllers/workspace_run_controller.py`) states an export size,
and the workspace code only ever asks for per-user quota sizes. The figure would be set on
the server side, in `applications/nfsserver/deploy/values.yaml` or `values-dev.yaml`;
those files were not read for this document, so the number is left unverified rather than
repeated.

## Platform state versus Argo state

### Persisted by the platform (Postgres)

Workspace identity, names, descriptions, ownership (`user_id`), `publicable`/`featured`,
collaborators, gallery images, tags, the optional `VolumeStorage` link, repository records
and — per workspace — the resource rows: name, type, status, origin JSON and folder.

The durable record of "what is in this workspace" is the `WorkspaceResourceEntity` rows,
and they are **regenerated from the volume**: a scan task publishes the file list to the
`osb-update-workspace-resources` queue (`workflow.py:85-91`) and the consumer rewrites the
resource rows (`workspaces/controllers/events.py:8-27`).

### Held in Argo (not persisted by OSB)

Every asynchronous action is an Argo workflow, created through CloudHarness
(`import cloudharness.workflows.argo_service as argo`, `crud_service.py:16`; `operations`,
`tasks` at `workflow.py:9-11`):

| Workflow | Created by | Basename |
| --- | --- | --- |
| resource copy / import | `run_copy_tasks` (`workflow.py:48-60`) via `copy_origins` (`etl_helpers.py:15-45`) | `osb-copy-tasks-job` |
| workspace clone content | `clone_workspaces_content` (`workflow.py:93-117`) | `osb-clone-workspace-job` |
| resource delete | `delete_resource` (`workflow.py:24-45`) | `osb-delete-resource-job` |
| notebook run | `run_notebooks` (`workflow.py:199-235`) | `osb-run-notebooks-job` |

There is no table for any of these. A notebook run's identity **is** the workflow name —
`run_notebooks` returns at once with `op.execute().name` and the controller returns it as
`WorkspaceRunResponse(workflow=run_id), 202`
(`workspaces/controllers/workspace_run_controller.py:142-145`).

Consequences that follow from the code:

- **Run history expires with the workflow.** `ttl_strategy` is `secondsAfterCompletion:
  3600`, `secondsAfterSuccess: 1200`, `secondsAfterFailure: 604800`
  (`workflow.py:17-21`). Once Argo garbage-collects a run, only its side effects remain:
  the files on the volume and the rescanned resource rows (the run pipeline's scan task is
  registered as Argo's `onExit` handler, `workflow.py:138-154`, `:225-234`).
- **"Is something running?" is a live cluster query, not a database lookup.**
  `WorkspaceService.get_workspace_workflows` lists Argo workflows by status
  (`crud_service.py:201-209`) and `get_notebook_run_workspaces` scans `Pending`/`Running`
  workflows by the `workspace` label (`workflow.py:186-196`). The run-concurrency guard is
  built on that (`workspace_run_controller.py:92-103`).
- **Argo being unreachable degrades to "nothing is running", it does not fail the read.**
  The workflow lookup in `WorkspaceService.get` is wrapped in `try/except` that logs and
  carries on (`crud_service.py:411-437`), and `get_workspace_workflows` returns `[]` on
  `AttributeError` (`:208-209`). So an import in progress may be invisible in the UI, and
  the concurrency limit cannot be enforced, but reads keep working.

### Kafka, only as glue

The event bus carries the scan result, not platform state: queues are declared in
`workspaces/controllers/events.py` (`DOWNLOAD_FILE_QUEUE = "osb-download-file-queue"`,
`UPDATE_WORKSPACES_RESOURCE_QUEUE = "osb-update-workspace-resources"`, `:8-9`), consumed by
`start_kafka_consumers` (`:30-36`) with handler `update_workspace_resources` (`:12-27`).
Message payloads are not persisted anywhere in this repository.

## Sizing and quota cross-references

All per-user sizes are computed at request time from Keycloak-backed quotas;
`devdocs/user-quotas.md` is the reference. The call sites, for traceability:

- PVC size: `get_pvc_size(user_id)` from `get_workspace_volume_size`
  (`crud_service.py:230-233`).
- Workspace count limit: `get_max_workspaces_for_user(user_id)` in
  `check_max_num_workspaces_per_user` (`crud_service.py:186-199`).
- Notebook-run pod resources: `get_notebook_run_resources(workspace.user_id)`
  (`workspace_run_controller.py:139-140`, `service/user_quota_service.py:24-29`).
- Concurrent-run limit: `get_max_concurrent_notebook_runs`
  (`workspace_run_controller.py:100-102`).

## Not determinable from the code consulted

Stated explicitly, so nothing below is mistaken for a finding:

1. **Column types, indexes, uniqueness and foreign keys.** `models.py` is generated
   typing; the DDL lives in OpenAlchemy's output from the OpenAPI schema
   (`applications/workspaces/api/openapi.yaml`, see `devdocs/api-contracts.md`) and is not
   spelled out here.
2. **The NFS export size (240Gi).** Not present in any file read for this document; see the
   NFS section above for where it would be configured.
3. **Database host, credentials and migrations.** The workspaces server's own
   `applications/workspaces/deploy/values.yaml` and the postgres deployment/secret were not
   read here, and no migration tool is referenced by `persistence/models.py`. Note that
   `applications/workspaces/server/test/values.yaml` contains live-looking credentials
   (Keycloak admin password, client secrets, DB password) — treat that file as test
   configuration that ships values, not as a template.
4. **Orphan-volume reaping.** No code found that reconciles PVCs with rows; the only
   deletion path is `WorkspaceService.delete`.
5. **`VolumeStorage` semantics.** The table exists and is administrator-only, but nothing
   read here shows how a `WorkspaceEntity` is bound to one.
6. **Retention of resource rows after a failed import.** `status` moves through `p`/`a`/`e`
   (`ResourceStatus`, `models.py:816-817`) but no cleanup of error rows was found.
